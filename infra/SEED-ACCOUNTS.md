# 프론트 테스트 계정 안내

`infra/seed-full-scenario.sql` 을 돌리면 만들어지는 데이터다.
스크립트는 멱등해서 몇 번을 실행해도 같은 상태가 되고, 기존 데이터는 지우거나 덮어쓰지 않는다.

```bash
psql "<연결 문자열>" -f infra/seed-full-scenario.sql
```

**적용 완료**: 로컬 DB, Railway DB(`drawing-diary-production.up.railway.app`) 둘 다 반영됐고
아래 API 로 확인까지 마쳤다.

> **user_id 와 diary_id 는 환경마다 다르다.** 로컬과 Railway 의 id 체계가 서로 달라서
> 스크립트가 이메일로만 사람을 찾는다. 화면에서 id 가 필요하면 로그인 응답의
> `userId` 를 쓰면 된다. 맨 아래 **부록**에 Railway 기준 실제 id 를 적어뒀다.

## 1. 계정 (비밀번호는 전부 `password123`)

### 주요 계정 4개

| 이메일 | 닉네임 | 이 계정으로 확인하기 좋은 것 |
|---|---|---|
| `test3@example.com` | 민서 | 기존 계정. 협업 일기 + 비공개 일기 + 방 초대 보낸 쪽 |
| `seed.yuna@example.com` | 유나 | 일기가 가장 많음(7건). 작업 중인 방의 방장 |
| `seed.dohyun@example.com` | 도현 | 팔로우가 비대칭이라 접근 거부(403) 화면 확인용 |
| `seed.sora@example.com` | 소라 | 안 읽은 알림만 있음. 받은 방 초대 2건 |

### 조연 6개 — `seed.reader1@example.com` ~ `seed.reader6@example.com`

닉네임 `구경꾼1` ~ `구경꾼6`. 비밀번호 동일.
좋아요 수를 0~8로 벌리려고 둔 계정이라 일기를 쓰지 않는다.
`구경꾼1`은 **팔로워가 0명**이라 "팔로워 없는 프로필" 화면을 볼 수 있다.

**예외 없이 10개 계정 전부 `password123`이다.** 스크립트가 실행될 때마다 위 10개
이메일의 비밀번호를 `password123`으로 맞추므로, 이 스크립트보다 먼저 있던
`test3@example.com` 도 포함된다. 누가 화면에서 비밀번호를 바꿔놨더라도
스크립트를 다시 돌리면 원래대로 돌아온다.

## 2. 계정별 상태

### 민서 (`test3@example.com`)
- **팔로잉(2)**: 유나, 도현 — 둘 다 맞팔
- **팔로워(6)**: 유나, 도현, 소라, 구경꾼1·2·6
- **일기 5건** (본인이 쓴 4 + 협업자로 참여 1)
  - PUBLIC 2건 — `새벽 네 시의 편의점`, `제주 돌담길`(협업: 도현)
  - FOLLOWERS_ONLY 1건 — `비 오는 날의 국물`
  - PRIVATE 1건 — `아직 정리 못 한 일기` (카테고리·태그 없음)
  - 협업 참여 1건 — 소라의 `셋이 같이 그린 여름` (3인 협업)
- **알림 26건**(안 읽음 6) — LIKE / COMMENT / FOLLOW 섞임
- **랭킹**: 본인 일기 4건이 3·4·7·8위에 걸려 있음 → `/api/rankings/me` 확인용
- 작업 중인 방 `미완성 야식 지도`의 **방장**, 도현에게 초대 보낸 상태(PENDING)

### 유나 (`seed.yuna@example.com`)
- **팔로잉(2)**: 민서, 도현 / **팔로워(4)**: 민서, 소라, 구경꾼1·4
- **일기 7건** (본인 5 + 협업 참여 2)
  - PUBLIC 3건 — `봄볕 드는 창가`(랭킹 1위), `라떼 아트 첫 성공`(협업: 도현), `오늘도 스쿼트 100개`
  - FOLLOWERS_ONLY 1건 — `창밖 고양이 관찰일지`
  - PRIVATE 1건 — `아무한테도 안 보여줄 낙서` (카테고리·태그 없음)
  - 협업 참여 2건 — 도현의 `한강 야경 자전거`, 소라의 `셋이 같이 그린 여름`
- **알림 28건**(안 읽음 19) — 가장 많음
- 작업 중인 방 `같이 그리는 가을 산책`의 **방장**, 소라에게 초대 보낸 상태(PENDING)
- `오늘도 스쿼트 100개`는 **PUBLIC인데 AI 점수가 없다** → 점수 없는 카드 처리 확인용

### 도현 (`seed.dohyun@example.com`)
- **팔로잉(2)**: 민서, 소라 / **팔로워(4)**: 민서, 유나, 구경꾼2·5
- **일기 5건** (본인 3 + 협업 참여 2)
  - PUBLIC 2건 — `한강 야경 자전거`(랭킹 2위, 협업: 유나), `강릉 바다 스케치`
  - FOLLOWERS_ONLY 1건 — `퇴근길 골목` (**카테고리 없음**)
- **유나를 팔로우하지 않는다** → 유나의 FOLLOWERS_ONLY 일기 조회 시 **403**
- `같이 그리는 가을 산책` 방의 멤버(수락 완료), `미완성 야식 지도` 초대 대기 중

### 소라 (`seed.sora@example.com`)
- **팔로잉(2)**: 민서, 유나 / **팔로워(3)**: 도현, 구경꾼3·6
- **일기 3건** — PUBLIC 2건(`야식 떡볶이 기록`, `셋이 같이 그린 여름` 3인 협업), PRIVATE 1건
- **알림 22건이 전부 안 읽음** → 안 읽음 뱃지·모두 읽기 버튼 확인용
- **받은 방 초대 2건(ROOM_INVITE 알림)**

## 3. 화면별로 뭘 볼 수 있는지

| 화면 | 확인 포인트 |
|---|---|
| 팔로잉 피드 `/api/feed` | 맞팔/단방향이 섞여 계정마다 목록이 다르다 (Railway: 민서 9건, 소라 16건) |
| 탐색 `/api/explore` | 카테고리 있는 것/없는 것, 태그 0~3개가 섞여 있다 |
| 랭킹 `/api/rankings` | 여러 건이 점수 내림차순으로 나온다 (Railway: 9건, 82~37점) |
| 알림 `/api/notifications` | FOLLOW / LIKE / COMMENT / ROOM_INVITE 4종, 읽음·안읽음 섞임 |
| 일기 상세 `/api/diaries/{id}` | 카테고리 있음/없음, 태그 있음/없음이 모두 존재 |
| 이어서 그리기 `/api/rooms/{id}/canvas` | WAITING 방 2개. `canvasData`(Base64)·`title`·`content` 다 채워져 있음 |
| 접근 제어 | PRIVATE·FOLLOWERS_ONLY 를 볼 수 없는 계정으로 열면 **403** |

### 캔버스 데이터 형식

`canvasData` 는 Base64 로 감싼 JSON 이다. 디코딩하면 이런 모양이다.

```json
{
  "version": 1, "width": 1080, "height": 1080,
  "strokes": [
    { "tool": "pencil", "color": "#3b3b3b", "size": 3,
      "points": [[120,540],[180,520],[240,530],[300,505]] }
  ]
}
```

형식은 서버가 강제하지 않는다(BYTEA 를 그대로 보관할 뿐이다).
프론트가 쓰는 형식이 다르면 `PUT /api/rooms/{roomId}/canvas` 로 덮어써도 된다.

## 4. 만들어진 데이터 요약

| | 개수 | 비고 |
|---|---|---|
| 계정 | 10 | 주요 4 + 구경꾼 6 |
| 팔로우 | 17 | 맞팔 2쌍 + 단방향 |
| 카테고리 | 13 | 계정당 3~4개 |
| 태그 | 10 | 일상·오운완·여행·맛집·카페·산책·비오는날·고양이·야경·드로잉 |
| 일기 | 15 | PUBLIC 9 / FOLLOWERS_ONLY 3 / PRIVATE 3, 협업 4건 |
| 일기-태그 연결 | 24 | 일기당 0~3개 |
| 좋아요 | 53 | 일기당 0~8개 |
| 댓글 | 27 | 일기당 0~5개 |
| AI 점수 | 8 | PUBLIC 9건 중 8건 (1건은 일부러 비움) |
| 작업 중인 방 | 2 | WAITING + canvas_data, 멤버 2명씩 |
| 방 초대 | 4 | ACCEPT 2 + PENDING 2 |
| 알림 | 101 | FOLLOW 17 / LIKE 53 / COMMENT 27 / ROOM_INVITE 4 |

### 데이터가 지키는 규칙

지어낸 값이 아니라 서버 로직과 아귀를 맞춰 넣었다.

- **좋아요·댓글은 그 일기를 실제로 볼 수 있는 사람만** 남겼다.
  "좋아요는 달렸는데 열면 403" 같은 상태가 없다.
- **`total_score` 는 `ScoreCalculator` 공식 그대로** 계산했다.
  `round(relevance*0.5 + color*0.3 + min(좋아요수*5,100)*0.2)`
- **작성자는 협업자 중 첫 번째**가 되도록 방장을 먼저 넣었다(`DiaryService.findAuthors`).
- **알림은 지어내지 않고** 위 팔로우·좋아요·댓글·초대에서 그대로 끌어냈다.
  타입별 `target_id` 도 각 서비스가 넣는 값과 같다(FOLLOW 만 null).

### 작업 중인 방 (이어서 그리기)

| roomId | 제목 | 방장 | 멤버 | 초대 대기 |
|---:|---|---|---|---|

### 랭킹 (`GET /api/rankings`)

9건이 순위대로 나온다 — 82 · 77 · 76 · 70 · 67 · 60 · **51** · 42 · 37.
7위 51점(`한강 자전거`)은 원래 있던 AI 점수이고, 나머지 8건이 이번에 넣은 것이다.

### 스크립트가 건드리는 기존 데이터

"추가만" 이 원칙이고, 기존 행을 고치는 곳은 아래 셋뿐이다.

1. 시드 계정 10개의 **비밀번호** → `password123` 으로 통일
2. 시드 계정의 `profile_img_url` / `bio` → **비었거나 `example.com` 가짜 URL일 때만** 채움
3. 시드 계정이 쓴 기존 일기의 `category_id` → **NULL 일 때만** 채움

세 경우 모두 대상이 위 10개 이메일로 고정돼 있어서, 다른 사용자의 데이터에는 닿지 않는다.
일기·좋아요·댓글·팔로우·알림을 **지우는 경로는 스크립트에 없다.**

> 닉네임은 스크립트가 **계정을 새로 만들 때만** 정한다. 이미 있는 계정의 닉네임은
> 건드리지 않는다. Railway 의 `test3@example.com` 은 원래 `수정된닉네임` 이었는데,
> 스크립트가 새 DB 에 만들 때 쓰는 값과 맞추려고 **한 번 수동으로** `민서` 로 바꿨다.
> 스크립트를 다시 돌려도 이 값은 그대로 유지된다.
